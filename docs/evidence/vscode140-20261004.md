# VS Code 1.140.0 on iPadOS 17 / macOS 14

## Package and scope

Microsoft's stable arm64 ZIP identifies version `1.140.0`, commit
`07f806f999227108933c2e30515b26eecc1fda74`, minimum macOS `12.0`.
Its SHA-256 matches Microsoft's update metadata:
`86a64f1cc9f4e0b5fc44969530994742f4bd61e7b98d9637238c5e24b26593b0`.
The bundle ships `Contents/MacOS/Code`, without the project's legacy
`Contents/MacOS/Electron` entry.

Framework UUID: `4C4C44E7-5555-3144-A1D4-12C2EFA5967E`.
The 1.130 manifest is deliberately rejected for this binary.

## Runtime and binary evidence

Runtime-confirmed via `Code-2026-10-04-111008.ips`: the unmodified framework
traps at image `+0x550ea10`; its caller returns to `+0x10b80fc`.
RE-confirmed via the actual framework:

```text
+0x10b8014 mov x1,#0x800000000     ; 32-GiB glued pool
+0x10b8018 mov x2,#0x800000000     ; 32-GiB alignment
+0x10b802c bl  +0x182a624          ; allocation
+0x10b8034 cbz x0,+0x10b80f8      ; real failure path
+0x10b80a4 mov x1,#0x400000000     ; 16-GiB metadata allocation
+0x10b80bc cbz x0,+0x10b80f8
+0x10b80e0 mov x13,#-0x400000000   ; metadata offset arithmetic
+0x10b80f8 bl +0x550e9d0          ; fatal allocation handler
```

The new manifest ports both core pools, all mask operations, two root
base-mask materializations, six folded superpage indices, metadata arithmetic,
and the complete Oilpan geometry together. Two additional register-form table
mask materializations at `+0x39fa4` and `+0x39fdc` feed the AND/index path at
`+0x39fa8`; they must follow the new eight-GiB core-pool size. Unrelated packed
ORR constants remain unchanged. The original framework is preserved.

RE-confirmed Oilpan reservation function: `+0x2027488`. It invokes allocator
virtual method `+0x30`, keeps the compressed-pointer sign-bit check at
`+0x20274ec`, and preserves the checked fallback and fatal paths. The useful
cage is four GiB with eight-GiB alignment and the existing shift-three pointer
ABI. The initial cage-base sentinel at `+0xb68e9c0` follows the same alignment.

The V8 allocator still overallocates for alignment. RE-confirmed constructor
`+0x62956a4` stores vtable address point `+0xb18fef8`; AllocatePages is slot
`+0xb18ff28`, targeting thunk `+0x62956e8`, which branches to `+0xbca2dc`.
That function adds `alignment - 1` to the requested size before mmap.
The existing exact-size adapter therefore needs a separately validated 1.140
profile. It retains the original allocator as fallback.

Runtime-confirmed via device `vscode140-backup-20261004/node-page-permissions.log`:

```text
[MacWSElectronPage] data page protection failed: 2 page=0x11c514000 size=16384 protection=0x1 maximum=0x3
Fatal error
Oilpan: Out of memory (Oilpan: CagedHeap reservation.)
```

Direct RW protection was also rejected in `node-direct-write.log`. A diagnostic
48-GiB hint still failed (`node-hint48.log`) and was reverted. This does not
establish a general kernel rejection mechanism.

The adapter now privately copies only the validated non-executable data page,
preserves every relocated byte except that one method pointer, and installs
the copy with its original read-only protection. Failed VM calls remain errors.
It does not modify executable memory or relax allocator checks.

Runtime-confirmed via `node-private-page.log`:

```text
EXIT 0
{"node":"24.21.0","electron":"43.7.3","arch":"arm64","heap":2536420}
[MacWSElectronPage] private data page copy: 0 slot=0x11c8dff28
```

The first GUI attempt reported `CodeWindow: renderer process gone (reason:
crashed, code: 6)` with the same Oilpan fatal. The 1.140 profile now covers its
renderer as well; the 1.130 UUID retains its previous Node-only scope.

## Verification

- Native Mach test exercises the actual private-page replacement: all other
  bytes remain exact, a mismatched original method leaves the page unchanged,
  and the final page is read-only.
- Exact reservation tests cover successful mappings, real-size requests,
  alignment rejection, original allocator fallback, errno and cleanup.
- Binary test applies the complete 37,572-instruction manifest to the original
  framework, checks unrelated constants, preserves the original, and rejects
  a different UUID without producing output.
- Both hook-library architectures and the host daemon build successfully.
- Actual VS Code CLI reports `1.140.0`, its commit above, and `arm64`, exit zero.
- The login-shell printer accepts `Code` and preserves token-framed JSON and a
  controlled marker. The returned environment is not logged.
- Authentic WindowServer capture `vscode140-frame.png` shows the welcome page,
  controls, text, icons, menu bar and Dock. This establishes visible rendering;
  it does not establish extension compatibility or general graphics stability.

The package, logs, and pre-deploy copies are retained under
`/var/jb/var/mobile/vscode140-backup-20261004` on the device. The original
Microsoft ZIP is preserved on the Mac. Account sign-in, extension marketplace
HTTPS, and embedded webviews need separate verification.

## CLI startup environment follow-up

Runtime-confirmed via `vscode140-cli-follow-up.log`: an ordinary chroot Bash
session running `code --help` without the GUI job's JIT environment traps:

```text
Fatal process out of memory: Failed to reserve virtual memory for CodeRange
```

The controlled repeat with `MACWS_JIT_MPROTECT_COMPAT=1` and
`MACWS_JIT_FAULT_WRITE_COMPAT=1` succeeds. The shipped mmap adapter in
`libmachook/mac_hooks.m` retries the rejected MAP_JIT reservation using the
existing tracked W^X mechanism only when that configuration is present.
This result concerns launch configuration; it does not demonstrate a random
allocator failure or establish the kernel's underlying rejection site.

`macws_code_cli.sh` now supplies these two settings to the vendor CLI child
and invokes the vendor script explicitly with Bash. It does not change the
parent shell or rewrite the vendor script. `configure_code_cli.sh` replaces
only the known vendor/managed symlink, preserving a custom CLI entry.
The Terminal setup helper installs this entry when the application exists.

Actual ordinary chroot Bash verification after installing the wrapper:

```text
help-exit=0
Visual Studio Code 1.140.0
1.140.0
07f806f999227108933c2e30515b26eecc1fda74
arm64
extensions-exit=0
```

Two executable tests cover quoted argument forwarding, child environment,
idempotent vendor-link migration, vendor preservation and custom-entry
preservation. The sixteen production-default checks also pass.
